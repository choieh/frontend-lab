# Frontend Lab · 강의 관리 대시보드

수강 중인 강의와 학습 진도를 확인하는 교육 서비스 대시보드입니다. HTML 마크업을 시작으로 SCSS 기반 반응형 화면, JavaScript 인터랙션, React 컴포넌트 구조로 발전시키는 개인 학습 프로젝트입니다.

웹 퍼블리싱 경험을 바탕으로 시맨틱 HTML과 접근성의 기본기를 점검하고, 프론트엔드 개발 범위를 단계적으로 넓히는 것을 목표로 합니다. 기능 구현뿐 아니라 요구사항 확인, 코드 리뷰, 수정 과정에서 내린 판단을 코드와 문서에 남깁니다.

> **현재 상태:** HTML 기반 화면 구조를 작성하는 단계입니다. 강의 카드는 반복 구조를 검토하기 위해 1개만 구현했습니다. 스타일과 인터랙션은 아직 적용하지 않았습니다.

## 화면 구성

| 영역 | 내용 |
| --- | --- |
| 사이트 머리말 | 서비스 이름 |
| 페이지 소개 | 페이지 제목과 안내 문구 |
| 학습 현황 | 전체 강의, 완료 강의, 진행 중인 강의 수 |
| 강의 목록 | 강의명, 강사, 학습 상태, 진행률, 상세보기 버튼 |
| 푸터 | 서비스 안내 문구 |

콘텐츠는 실습용 예시 데이터입니다. 통계는 전체 강의 6개를 기준으로 하며, 완료 2개·진행 중 3개·시작 전 1개로 구성됩니다. 현재 화면에 구현된 카드 수와 전체 데이터 수는 다릅니다.

## 현재 코드 구조

현재 구현 파일은 저장소 루트의 `index.html`입니다. 아래는 폴더 구성이 아닌 문서 내부의 역할 구조입니다.

```text
index.html
├── site-header         사이트 머리말
├── main
│   ├── page-intro      페이지 제목과 소개
│   ├── learning-status 학습 현황
│   └── course-list     강의 목록
│       └── course-card 강의 정보와 진행률
└── site-footer         사이트 푸터
```

현재는 하나의 HTML 파일에서 각 영역의 책임과 반복 구조를 먼저 정리하고 있습니다. SCSS와 JavaScript 파일 구성, React 전환 시의 디렉터리 구조는 해당 단계에서 결정합니다.

## 마크업과 접근성 설계

### 콘텐츠 역할에 맞는 요소 선택

페이지의 주요 콘텐츠는 `main`에 배치하고, 소개 영역은 내부 `header`, 학습 현황과 강의 목록은 각각 `section`으로 구분했습니다. 사이트 전체의 머리말과 본문 도입부가 서로 다른 범위를 갖도록 구성했습니다.

제목은 페이지 제목 `h1`, 영역 제목 `h2`, 강의 제목 `h3` 순서로 작성했습니다. 통계와 강의 목록은 `ul/li`로 묶어 항목의 집합이라는 의미를 전달합니다.

### 기본 HTML 요소 우선 사용

진행률은 빈 요소를 시각적으로 꾸미는 방식에서 `progress`를 사용하는 구조로 변경했습니다. `max`와 `value`로 수치를 전달하고, 화면에도 퍼센트 텍스트를 제공합니다.

상세보기는 `button`을 사용합니다. 아직 기능을 구현하지 않았으므로 `disabled`로 실제 사용 불가 상태를 표현하고 안내 문구를 제공합니다.

### 제목을 재사용하는 접근 가능한 이름

처음에는 진도와 버튼의 이름을 `aria-label`에 직접 작성했습니다. 이후 강의 제목이 변경될 때 같은 문구를 여러 곳에서 수정해야 하는 문제를 고려해 `aria-labelledby`로 변경했습니다.

```html
<h3 id="course-01-title" class="course-card__title">
    HTML 시맨틱 마크업
</h3>

<button
    class="course-card__detail-button"
    type="button"
    disabled
    aria-labelledby="course-01-title course-01-detail-label"
>
    <span id="course-01-detail-label" class="course-card__detail-label">
        상세보기
    </span>
</button>
```

버튼의 이름은 연결된 강의 제목과 “상세보기” 텍스트로 구성됩니다. 제목이 바뀌어도 별도 이름 문자열을 수정하지 않도록 했습니다. 카드를 확장할 때에는 ID와 참조를 함께 변경해 중복을 방지합니다.

## 클래스 명명 규칙

SCSS 작업과 반복 컴포넌트 관리를 고려해 BEM을 사용합니다.

```text
block
block__element
block--modifier
block__element--modifier
```

| 블록 | 책임 | 예시 |
| --- | --- | --- |
| `dashboard` | 전체 레이아웃 | `dashboard__main` |
| `site-header` | 사이트 머리말 | `site-header__brand` |
| `page-intro` | 제목과 소개 | `page-intro__title` |
| `learning-status` | 학습 현황 | `learning-status__label` |
| `course-list` | 강의 목록과 배치 | `course-list__item` |
| `course-card` | 개별 강의 정보 | `course-card__progress-bar` |
| `site-footer` | 푸터 | `site-footer__description` |

클래스는 여러 요소에서 재사용하고, ID는 문서 안에서 고유하게 관리합니다. 스타일 선택자는 클래스를 기준으로 작성할 계획입니다.

카드에는 `course-list__item course-card`를 함께 지정해 목록 내 배치와 카드 내부 표현의 책임을 구분했습니다. 요소 이름은 `course-card__progress-label`처럼 블록 기준으로 작성하며, DOM 깊이에 따라 `__`를 반복해 연결하지 않습니다.

SCSS에서는 아래와 같이 블록별로 관리할 예정입니다. 상태 modifier는 실제 변형이 필요할 때 추가하고, 비활성 버튼은 `:disabled`를 활용합니다.

```scss
.course-card {
  &__title {
    // 제목 스타일
  }

  &__detail-button {
    &:disabled {
      // 비활성 상태 스타일
    }
  }
}
```

## 작업 과정과 역할

이 프로젝트는 직접 작성한 코드를 리뷰하고 수정하는 방식으로 진행합니다.

1. 화면 시안과 요구사항을 확인하고 작업 범위를 정합니다.
2. GitHub Issue를 기준으로 작업 브랜치에서 구현합니다.
3. 반복되는 강의 카드는 하나를 먼저 작성해 구조를 검토합니다.
4. 시맨틱 요소, 제목 계층, 접근성, 유지보수 관점으로 리뷰합니다.
5. 피드백을 반영하고 선택한 구조와 규칙을 문서화합니다.

초기 HTML은 직접 작성했으며, Codex를 활용해 디자인·요구사항 자료 준비, 코드 리뷰, 일부 마크업 수정과 문서화를 진행했습니다. 리뷰 과정에서 이해하기 어려운 부분을 질문하고, ARIA 연결 방식과 클래스 규칙의 이유를 확인하면서 반영했습니다.

현재 HTML 작업은 `feature/day01-html` 브랜치를 기준으로 진행합니다.

## 커밋 메시지 규칙

커밋 제목은 `타입: 변경 내용` 형식으로 작성합니다. 변경 내용은 한국어로 간결하게 쓰고, 날짜나 DAY 번호보다 무엇을 변경했는지 드러내는 표현을 사용합니다.

| 타입 | 사용 기준 | 예시 |
| --- | --- | --- |
| `feat` | 새로운 화면이나 기능 추가 | `feat: 강의 대시보드 HTML 구조 구현` |
| `fix` | 오류 또는 누락 수정 | `fix: 강의 진도와 상세보기의 접근성 이름 연결` |
| `refactor` | 기능을 유지하면서 코드 구조 개선 | `refactor: 대시보드 클래스를 BEM 규칙으로 통일` |
| `style` | 들여쓰기 등 코드 서식 변경 | `style: HTML 들여쓰기 통일` |
| `docs` | README 등 문서 변경 | `docs: 프로젝트 소개와 개발 규칙 작성` |
| `chore` | 개발 설정 및 도구 관리 | `chore: SCSS 컴파일 환경 설정` |

`style`은 CSS 구현을 뜻하지 않습니다. 새로운 반응형 화면 구현은 `feat`, 레이아웃 오류 수정은 `fix`로 구분합니다.

### 작성 원칙

- 하나의 커밋에는 하나의 목적을 담습니다. HTML 구현과 README 작성은 가능한 한 별도 커밋으로 나눕니다.
- 제목만 읽어도 변경 내용을 알 수 있도록 작성합니다. `수정`, `작업 완료`, `최종` 같은 모호한 제목은 피합니다.
- 설명이 필요하면 제목 아래 한 줄을 비우고 본문에 주요 변경 내용과 이유를 적습니다.
- 아직 커밋하지 않은 초기 구현은 최종 결과를 기준으로 묶습니다. 중간 수정 과정을 인위적으로 나누지 않습니다.
- 진행 중인 이슈는 본문에 `Refs #이슈번호`로 연결합니다. 완료 기준을 충족한 뒤 최종 PR에 `Closes #이슈번호`를 사용합니다.

### 예시: 초기 HTML 구현

```text
feat: 강의 대시보드 기본 HTML 구조 구현

- 페이지 소개와 학습 현황, 강의 카드 1개 구성
- 진도와 상세보기 버튼에 접근성 이름 연결
- BEM 클래스 명명 규칙 적용
- 나머지 강의 카드와 SCSS 작업은 후속 진행

Refs #1
```

### 예시: 프로젝트 문서 작성

```text
docs: 프로젝트 소개와 구현 원칙 정리

- 프로젝트 목적과 현재 구현 상태 설명
- 시맨틱 마크업과 접근성 설계 의도 기록
- BEM 규칙과 향후 개발 계획 정리
```
